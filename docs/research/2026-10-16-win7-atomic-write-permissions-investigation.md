# Win7 原子写临时目录权限问题调查

日期：2026-10-16。调查起点：`6152611d3c259dbe1fd4971460039c87e0a3b259`。性质：代码审查、真实 NTFS 受控实验及用户认可后的局部加固。用户确认内网诊断已验证 ACL 限制，并通过命令行 ACL 操作删除残留；未取得现场 Win7 错误号、具体 ACE 或继承配置，不能判定具体失败阶段。后续实现见“已实施调整”；原 Portable ZIP 未重建，不包含本次修复。

## 现场现象与结论

用户在 Win7 实测 rc.1 基线 Portable，基本功能正常。在 `workspace-write` 下，某目录编辑已有文件偶发权限失败，留下 `.文件名.PID.UUID.tmpdir`；同目录直接新建 probe 也能失败，换到另一测试目录读写正常。残留有时无法在资源管理器删除。现场位于内网，无法导出原始材料；用户先怀疑只读属性，后确认内网智能体已验证 ACL 限制，并经 ACL 操作删除残留。

结论：**根据用户提供的内网验证结果，现场属于 ACL 限制；本机另有可重复的目录 ACL 继承/删除限制路径，能解释上述组合。**本机具体 ACE 组合仍只是现场机理的候选，不能冒充现场采样。单个目标文件的只读属性不能独立解释同目录新建也失败。是否另有占用句柄等叠加因素，没有现场证据。

目录属性中的“只读”、文件本身的只读位、ACL 的只读授权和产品 `read-only` 模式是不同机制。不能因为资源管理器目录属性中的方框就认定该目录不能创建文件。

## 代码路径

- [文件沙箱](../../dsh/fs/fs_sandbox.py)：`workspace-write` 对目标进行规范路径/可写根检查，然后在宿主进程委托给本地 FS；这条 write/edit 链不通过受限 token runner。
- [本地 FS](../../dsh/fs/fs_local.py)：`writeText` / `editText` → `_atomic_write`，先在目标父目录创建随机 `.tmpdir`，再创建独占临时文件、写入、同步、关闭，最后发布。
- Windows 上新建对象使用继承/default 安全描述符；Python 3.8 代码中的目录 `0o700` 不等于安装一个只允许当前用户的 NTFS DACL。
- 覆盖已有文件时，`_copy_windows_dacl` 只将目标文件的 DACL 复制到**临时文件**并保护其不再继承；不复制 owner，也不修改暂存目录的 ACL。
- 已有目标使用 `ReplaceFileW`；新文件通常用 rename，有 `createIfAbsent` 意图时使用硬链接。具有“写入数据”权限不一定具有原子替换、重命名和删除权限。
- 调查起点的 `_remove_staging` 使用严格 `shutil.rmtree`。继承 ACL 禁止删除时清理同样失败，错误包含原始失败及清理失败。其上游兼容错误码为 `FS_NOT_FOUND`，不能把这个外层码当成真正的文件不存在；后续已改为有身份检查的非递归清理，见下文。
- 每次调用都生成新的 UUID，不会固定重用某个旧 `.tmpdir`。持续失败可能是各次创建都继承相同限制，不能单凭残留推断旧临时目录锁死了下一次操作。

从切换前 `38e650cf` 到调查起点 `6152611d`，`dsh/fs/fs_local.py`、`dsh/fs/fs_sandbox.py`、`dsh/sandbox/windows_acl.py` 均无差异。没有证明这是 rc.1 引入的新缺陷，也没有证明既有 1175 观察与此次现场故障同因。后续改动仅涉及本地 FS 的失败处理及测试，没有修改沙箱 ACL 提供端。

## 固定原版 rc.1 的处理

比较对象为迁移固定的 `dsh-v0.1.2-rc.1`（`a66e4702047846cdaa10c66c9d3df3951f5ea70d`），不是未经检查的后续上游版本。

- [原版 fsio.ts](../../packages/fs/fs-local/src/fsio.ts) 的 `writeFileAtomic` 同样创建同目录随机暂存目录，独占创建临时文件；覆盖时先复制目标 DACL，写入并同步、关闭后调用 `ReplaceFileW`。新建文件继承目录策略；没有为每次写入自动授予当前用户全控制，也没有自动修复父目录 ACL。
- [原版 win32.ts](../../packages/fs/fs-local/src/win32.ts) 同样使用 `GetFileSecurityW` / `SetFileSecurityW`，只复制 DACL，并加 `PROTECTED_DACL_SECURITY_INFORMATION` 禁止继承扩大授权。`ReplaceFileW` 的 flags 为 0，不启用忽略 ACL 错误。
- [原版设计说明](../../reference/.agents/notes/implemented/bug-fix/2026-07-19-windows-atomic-write-dacl-preservation.zh.md) 明确解释：目标文件可能比父目录更保密，因此必须在空临时文件上先安装目标 DACL，再写内容；不能先按宽松父目录 ACL 写完再修权限。它还明确拒绝每次设置仅所有者 DACL，因为那会破坏有意配置的项目共享权限。
- 原版失败时通过 `rm({recursive:true, force:true})` 尝试清理；若清理也失败，`removeStagingDirOrThrow` 同样把双重错误包装为 `FS_NOT_FOUND`。`force` 不代表绕过 Windows ACL。调查起点的本机使用 `shutil.rmtree`，不能据此声称两种运行时的全部清理细节相同，但原版也没有权限接管或自动重写 ACL 的分支。

因此，本地实现保留了原版的关键权限策略。源码支持“原版也受同类权限边界约束”，但本次没有执行原版在上述限制 ACL 下的逐例对照，不能声称已证实其错误文本和残留完全相同。

## 产生机理及责任边界

原子写不是一次“打开目标写内容”，而是一组独立授权操作：创建暂存目录 → 在其内创建文件 → 安装目标 DACL（覆盖时）→ 写入 → 重命名/替换 → 删除暂存对象。ACL 可以允许其中一部分，同时拒绝另一部分。

1. 父目录允许创建子目录，不意味着子目录继承后仍允许当前用户创建子文件或删除该目录。带不同 OI/CI/IO 范围的 ACE 足以形成这个结果；受控第六组正是“创建了目录但不能继续写，也不能清理”。
2. 允许文件数据写入，不等于允许 DELETE、父目录 DELETE_CHILD 或 DACL 修改。受控第七组可以创建并写入，却在发布和清理时失败。`ReplaceFileW` 还会为保存元数据请求相应访问权。
3. 覆盖路径先把原目标的受保护 DACL 安装到临时文件上，也可能使后续按路径重新打开、替换、删除临时文件更受限制。创建时已经取得的写句柄与后续重新访问的授权不是同一次检查；不能由“内容写进去过”推断随后可删除。
4. 对象由当前进程创建，不等于当前用户必然拥有该对象的所有访问权；本路径也没有把目标 owner 复制给暂存对象。因此现有证据不足以认定程序把文件关联到了错误用户。`workspace-write` 是应用层路径授权，不授予 Windows 原本没有的 ACL 权限。

这是**目录权限与原子写所需能力不匹配，加上失败清理/诊断边界不足**。目录可能按企业策略有意禁止删除，不能直接定性为用户“配置错误”；这样的目录确实不适合现有原子替换契约。反过来，应用在失败后留下难诊断、难清理的自建对象，也值得改善，不能完全交给用户善后。

环境：Windows build 26200、本项目 Python 3.8.10 x64、真实 NTFS。以下均调用生产 `FsService.writeText`，每组顺序执行“编辑已有文件 → 新建 probe → 再编辑已有文件”，共七组、21次调用。未声称在 Win7 上复现。

| 控制条件 | 编辑已有文件 | 新建 probe | 暂存残留 |
|---|---|---|---|
| 正常目录/文件 | 成功 | 成功 | 无 |
| 只有目标文件 READONLY 属性 | `ReplaceFileW` Win32 5 | 成功 | 无 |
| 只有目录 READONLY 属性（实测 attributes=17） | 成功 | 成功 | 无 |
| 目标被不允许 delete sharing 的读取句柄占用 | `ReplaceFileW` Win32 32 | 成功 | 无 |

## 内网只读检查

在启动 Portable 的同一个普通用户控制台，替换下面路径。命令只读取状态，不修改属性或权限，也不读取文件正文；无需将输出导出内网。

```bat
whoami /user
attrib "D:\项目\出问题的目录"
attrib "D:\项目\出问题的目录\目标文件.txt"
icacls "D:\项目\出问题的目录"
icacls "D:\项目\出问题的目录\目标文件.txt"
icacls "D:\项目\出问题的目录\.目标文件.txt.PID.UUID.tmpdir"
icacls "D:\项目\出问题的目录\.目标文件.txt.PID.UUID.tmpdir\目标文件.txt.tmp"
```

优先比较正常目录和失败目录：

1. 目标文件是否有 `R` 属性；残留临时文件是否也有 `R`。目录的 `R` 不足以证明文件不能写入。
2. 当前用户或所属有效组在目录及其后代上是否有 `(M)` / `(F)`，是否存在拒绝 ACE，`(OI)` / `(CI)` / `(IO)` / `(I)` 的继承范围是否不同。只看到一个 allow 行不能替代完整有效权限判断。
3. `.tmpdir` 的授权是否比父目录更窄；是否具有创建子文件、删除自身/子文件所需权限。创建成功、写入失败和删除失败是三个不同检查。
4. WinError 5 表示访问拒绝，但可由属性或 ACL 等产生；WinError 32 是 sharing violation；1175 是替换时无法移除旧文件。这些不能混为“申请用户权限失败”。

单个目标文件确有 `R` 时，可在确认该文件本来应可编辑后，通过文件属性对**这个文件**解除只读再试。如果同目录新建 probe 仍失败，应继续检查目录 ACL/继承；不应自动递归清除整个工程的属性、接管所有权或授予 Everyone 全控制。

## 修复边界与后续

本次先保留严格拒绝及既有权限策略。直接放宽目标 ACL、跳过 DACL 保留、失败后非原子覆盖、无条件重试 WinError 5，都不能作为已证实的修复。现场已确认 ACL 限制，环境侧应由有权限的维护者核对这个工作区所期望的当前用户“修改”权限及对子目录/文件的继承范围，同时检查显式拒绝与目标受保护 DACL；不是只在父目录添加一条允许就能保证有效。显式禁止删除的目录无法保证现有原子发布契约。

实施前的建议优先级如下；实际完成范围单独记录于下节，不自动修复用户权限：

| 优先级 | 行动 | 验收边界 |
|---|---|---|
| P0 | 增加阶段、路径、原始 WinError、主失败/清理失败及残留路径诊断，避免外层 `FS_NOT_FOUND` 误导智能体持续重试 | 保持原版契约码兼容；覆盖两类 ACL 失败、只读、占用及正常路径的实际回归 |
| P1 | 评估仅对本次确证自有暂存对象保留清理能力，或在写内容前更早发现无法继续的权限限制 | 不修改目标/父目录授权，不扩大暂存内容可见性；验证重解析点、路径替换及异常退出；必须做 Win7/Python 3.8 实测 |
| 运维 | 为应当可编辑的工作区配置适当的有效权限与继承，修复已确认的自有残留 | 按具体目录处理，不递归重置整个用户目录，不授予 Everyone 全控制 |

P1 不是“加一条 icacls”即可解决：可研究在创建自有对象时取得合法的删除/安全描述符操作能力，但不能假设 ACL 始终允许；`ReplaceFileW` 对临时文件的打开共享要求也需要核实，不能简单持有额外句柄跨越发布。预检查存在检查与使用之间的竞争，不能替代每一步失败处理。没有合法删除能力时，程序只能安全失败并告知残留位置，不能承诺自动清理成功。

任何自动清理都需区分原有目标与自有暂存对象，并拒绝链接/未知文件；清理只读位不能解决 ACL 拒绝。保留当前 DACL 安全语义，另加诊断与受限清理保护，是建议路径。微软另列出 `ReplaceFileW` 1176/1177 的部分完成状态，因此不能笼统承诺所有替换失败都保留原文件；若后续实现恢复机制，应把这些状态与普通访问拒绝分开处理。

## 已实施调整

用户认可后，第一步已实施于 [fs_local.py](../../dsh/fs/fs_local.py)，定向新增用例见 [test_fs_atomic_write_diagnostics.py](../../tests/test_fs_atomic_write_diagnostics.py)。新增异常诊断字段与失败消息属于本地增强；暂存目录位置、独占创建、覆盖前复制受保护 DACL、同步/关闭、`ReplaceFileW` flags=0、仅 ENOENT 回退 rename、guarded create 的硬链接发布均保持原版策略。原版源码和前端未修改。

1. 每个原子写失败附带 `atomicWrite` 诊断，记录阶段、目标/暂存/临时文件路径、原始错误字段、清理状态及独立清理错误。I/O 失败的 `message` 增补阶段及处理提示，实际工具错误渲染可直接显示；不改变原异常身份、已有契约码或 cause。原版观察冲突/版本过期/取消的普通消息保持。
2. 清理前核验本次记录的目录和文件设备/inode、类型，拒绝重解析点、未知条目及身份改变；只 unlink 已知临时文件并 rmdir 空目录，不再递归删除。身份缺失/为零也保守拒绝。路径核验不能消除检查与使用之间的竞争，不将其宣称为新的内核隔离边界。
3. 保留写入主错误，即使随后关闭句柄也失败；主失败和清理失败同时出现时仍沿用原版 `FS_NOT_FOUND` 外层契约码，但消息和结构化诊断明确保留两者。
4. 对 `ReplaceFileW` 的 1176/1177 保留暂存对象并提示检查目标/暂存状态后恢复，不自动回退覆盖或重试。这里是按微软文档状态进行注入验证，未声称在真机强制制造了这两个底层错误。
5. 发布成功后清理失败只写 warning，不将成功写入改报失败；日志包含阶段和残留路径，日志处理器异常也不推翻成功结果。该 warning 是宿主日志，不向成功工具输出增加字段。

不自动调整父目录/目标/暂存 ACL、不提权、不清除只读位、不扫描历史 `.tmpdir`。ACL 确实禁止删除时仍可能残留；需要有权限的维护者按具体现场处理。第二步“创建时保留合法清理能力”的 Win32 句柄/安全描述符方案仍延期，须单独设计并在 Win7 验证。
